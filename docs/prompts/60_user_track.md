# 60 — The SQL and SimPy track (ADR-0010, superseded for these files by ADR-0022)

Five pieces of this project form a second implementation beside the TypeScript engine: the canonical DDL, three core SQL queries, and the SimPy core loop. ADR-0010 assigned them to the author, by hand. ADR-0022 (accepted 2026-11-03) has AI write them, clean-room from the specification (the design documents, the schemas, the fixtures and the acceptance tests; never `engine/src/` or `src/`), and every text that names them says that the author did not write them. The acceptance tests are written before the files and are never edited to make the files pass. The author may write their own version later and replace these files; the same tests judge it. The learning paths and the "for you" questions in the cards are for whoever writes a version by hand.

Read `docs/prompts/00_master_build.md` first. This file is for (a) the executor that writes the five files, or the author who replaces them, (b) S1a/S2 executors, who build the acceptance tests named here, and (c) any AI asked to review these files. Names come from `docs/design/data_model.md`; if a card and that file disagree, the design wins and the orchestrator fixes the card.

## Task cards

### Card A — canonical DDL, `reference/sql/schema.sql` (about 3-4 h including reading)

- **Goal:** one schema that holds the recorded world for the C architecture and can also hold A and B data with gaps, so the same queries run on all three. DuckDB dialect, written in standard SQL so it ports to Postgres.
- **Inputs:** `docs/design/data_model.md` (entities, key constraints K1 to K14, time fields, state machines, validation catalogue), `data/schemas/event.schema.json`, `docs/adr/` (stack).
- **Hard constraints from the design:** `(request_id, analyte, version)` unique in `result` (K1); `measured_at` and `run_id` `NOT NULL` in `result` (K2); `sampled_at` exists only in `sample` (K3) and is stored only when `two_clocks` is on, so the column is nullable; `hold_time` and `turnaround` are derived (data_model §5), never stored; time columns `TIMESTAMP`; versions append-only (no update path in the model); five time meanings kept apart: `sampled_at`, `measured_at`, `ingested_at`, `reviewed_at`, `available_at`.
- **Names the acceptance test requires** (a minimum; everything else is yours to design). Tables and columns: `unit(unit_id, unit_tag)`; `batch(batch_id, unit_id, inoculated_at, harvested_at)`; `process_event(event_id, batch_id, unit_id, type, occurred_at)`; `operator(operator_id)`; `method(method_id, version)`; `sample(sample_id, unit_id, batch_id, sampled_at, operator_id, volume_ul, state)`; `aliquot(aliquot_id, sample_id, volume_ul, state)`; `analysis_request(request_id, aliquot_id, method_id, state, control_id NULL)`; `instrument(instrument_id)`; `instrument_state(instrument_state_id, instrument_id, valid_from, reagent_lot, calibration_ref)`; `run(run_id, instrument_id, instrument_state_id, method_id, started_at, ended_at, operator_id)`; `result(result_id, request_id, analyte, version, run_id, value, unit_ucum, measured_at, ingested_at, reviewed_at, available_at, state)`; `lineage_edge(edge_id, from_item_id, to_item_id, relation, occurred_at, available_at)`; `historian_value(tag, ts, value, ingested_at)` (`ts` is validity time, `ingested_at` transaction time). The names are those of `data_model.md` §2, §3 and §5. `unit_tag` is a column of `unit` (the historian tag prefix; a historian tag is `unit_tag`, a dot and a signal name, for example `U03.pH`), not a table.
- **Decide and record in your header comment:** which time-order rules of data_model §5 are `CHECK` constraints and which are only validation queries (the recorded world must be able to hold wrong data so the wrongness can be detected; K4, `sampled_at <= run_started_at <= measured_at`, spans three tables and cannot be a `CHECK`); which keys are natural versus surrogate; how `state` and closed lists such as `lineage_edge.relation` are constrained (use `TEXT` with `CHECK (... IN (...))`, data_model §13; `ENUM` types are on the deny-list so the DDL stays portable); how columns you add stay compatible with the fixtures (they must be nullable or have defaults, because the fixtures insert with explicit column lists).
- **Acceptance** (`tests/user_track/test_schema_sql.py`): (1) the file executes cleanly in in-memory DuckDB; (2) the required names exist; (3) a duplicate `(request_id, analyte, version)` is rejected and a `NULL` `run_id` or `measured_at` is rejected; (4) `sampled_at` appears only on `sample` and time columns are `TIMESTAMP`-typed; (5) `tests/fixtures/sql/single_sample.sql` loads (explicit column lists); (6) no deny-listed non-portable construct (`CREATE OR REPLACE`, `INSTALL`, `LOAD`, `STRUCT`, `MAP(`, `LIST(`, array `[]` types, `ENUM(`, `UNION(`, `USING SAMPLE`); (7) integrity checks as test queries, because DuckDB has no triggers: each is a `SELECT` of violating rows in `tests/fixtures/sql/integrity/`, run against a good dataset (expects 0 rows) and a bad dataset (expects at least 1) loaded through your schema. The checks (data_model §13): K5, K8 and K13 immutability, as a comparison of two snapshots in which a row present in both with different protected columns is a violation; K6 two open batches on one unit; K7 two overlapping runs on one instrument (`run.started_at`, `run.ended_at`); K10 a cycle in `lineage_edge`; K12 aliquot volumes above the sample volume. K6 uses `batch.inoculated_at` and `batch.harvested_at`, K12 uses `sample.volume_ul` and `aliquot.volume_ul` (required names above; the columns are nullable because the recorded world may lack them). The checks need no code from you beyond the required columns.
- **Learning path:** DuckDB docs, "Data Types" and "Constraints" (`PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `CHECK`, foreign keys and their limits); PostgreSQL docs, "Data Definition" for the portable subset; then read the single-sample example in `docs/design/data_model.md` and sketch the rows for A, B and C on paper first.

### Card B1 — `reference/sql/queries/asof_join.sql` (S2; about 2-3 h)

- **Goal:** for every result known at a decision time, attach the historian value that was effective **at `sampled_at`** and **known at that decision time**. Never join on `measured_at`.
- **Parameters:** `$decision_time` (timestamp), `$max_age_s` (integer; older matches return `NULL`).
- **Output columns:** `request_id, analyte, version, tag, ctx_ts, ctx_value`, one row per `(request_id, analyte)` known at the decision time, per tag of its unit (`historian_value.tag` is `unit.unit_tag`, a dot and a signal name).
- **Rules (the as-of rule of `data_model.md` §5):** (1) reduce `result` to the latest version per `(request_id, analyte)` with `available_at <= $decision_time`; (2) reduce `historian_value` to rows with `ingested_at <= $decision_time` and, per `(tag, ts)`, the latest ingested row; (3) `ASOF JOIN` on `ts <= sampled_at`, reaching `sampled_at` through request, aliquot and sample. Record in your header how `state` filtering works; the fixture avoids that question.
- **Hand fixture** (typed by the executor in `tests/fixtures/sql/`): one unit `U03` (`unit_tag` `U03`) with historian tag `U03.pH`; historian rows `(08:30, 1.0, ingested 08:30:10)`, `(08:39, 2.0, ingested 08:39:10)`, `(08:39, 2.5, ingested 10:30:00)` (a late correction), `(09:00, 5.0, ingested 09:00:10)`; one result sampled 08:40:00, measured 09:25:00, version 1 with `available_at` 09:30:00 and version 2 (a correction) with `available_at` 10:30:00. Expected: decision 09:00:00 gives no row (no result known yet); 10:00:00 gives version 1 with `2.0`; 10:29:59 the same; 10:30:00 gives version 2 with `2.5` (the boundary is `<=`); 11:00:00 gives version 2 with `2.5`. `$max_age_s = 30` gives `NULL` for `ctx_value` (the match is 60 s old) and `60` keeps it. The test also asserts the value is never `5.0`, which is what a `measured_at` join would return, and that a future version never appears before its `available_at`. A second result whose sample has no `sampled_at` (`two_clocks` off) yields `NULL` context, never a `measured_at` match.
- **Learning path:** DuckDB docs, "ASOF Join" (inequality condition, `USING` form); first write the same thing with pandas `merge_asof` on the fixture and compare; then read about valid time versus transaction time (bitemporal) in `docs/design/data_model.md` §5.

### Card B2 — `reference/sql/queries/lineage_recursive.sql` (S2; about 2-3 h)

- **Goal:** all ancestors of an item through `lineage_edge`, one row per distinct ancestor at its minimum depth, safe against cycles.
- **Parameters:** `$root_id`, `$max_depth`. **Output:** `ancestor_id, depth`, ordered by `depth, ancestor_id`. The root is never its own ancestor, even when a cycle leads back to it.
- **Hand fixture:** edges (`from_item_id` to `to_item_id`; any `relation` from the data_model §12 list, the query ignores it): `S1>A1`, `S2>A2`, `A1>P1`, `A2>P1`, `P1>P1a`, `P1>P1b`, `P1a>P2`, `P1b>P2`. Root `P2`, depth cap 10, expected `(P1a,1) (P1b,1) (P1,2) (A1,3) (A2,3) (S1,4) (S2,4)`. With `$max_depth = 2`: the first three rows. A second fixture adds the bad edge `P2>P1` (a cycle that K10 forbids in valid data): the query must terminate and return the same seven rows.
- **Learning path:** DuckDB docs, "WITH Clause", recursive CTEs, and the section on avoiding infinite recursion; PostgreSQL docs, "WITH Queries", the `CYCLE` clause and path-array technique. Do the closure by hand on paper for the fixture before writing SQL.

### Card B3 — `reference/sql/queries/bridging_offset.sql` (S2; about 1.5-2 h)

- **Goal:** estimate the inter-instrument offset per analyte from control material measured on both instruments after a lot change, and return corrected values for the target instrument. No evidence means no correction.
- **Parameters:** `$reference_instrument`, `$target_instrument`, `$changeover_at`.
- **Rule:** `offset(analyte)` = mean over control ids of `[mean(target values) - mean(reference values)]`, using results (through `run.instrument_id`) with `measured_at` at or after `$changeover_at`. Control material is marked by `analysis_request.control_id`. Correct only target-instrument results at or after `$changeover_at`. The fixture has one version per result; record in your header what you do with superseded versions.
- **Output:** `request_id, analyte, version, instrument_id, value_raw, offset_applied, value_corrected, n_controls`. Where no offset is estimable: `offset_applied` and `value_corrected` are `NULL`, never silently equal to raw.
- **Hand fixture:** analyte glucose; control C1 reference `[10.0, 10.2]`, target `[10.6, 10.8]`; control C2 reference `[5.0]`, target `[5.4]`. Per-control differences 0.6 and 0.4, offset 0.5, `n_controls = 2`. Target results after the changeover `8.0, 6.5` become `7.5, 6.0`; target results before it and reference results are unchanged; a second analyte without controls yields `NULL`. Tolerance 1e-9.
- **Learning path:** DuckDB docs, aggregates and `GROUP BY`, window functions; read about bridging or method-comparison studies in the cited sources in `docs/research/sources.yaml` (grep for "bridging"); sketch the two-level mean on paper first.

### Card C — `reference/simpy/sim_core.py` (S1a; about 5-7 h including learning)

- **Goal:** a SimPy 4.1.2 model of L3 that reads a trace (`data/schemas/trace.schema.json`), applies the semantics of the contract table in `docs/prompts/10_S1a_contracts_analyzer.md` Step 1, and writes a result (`data/schemas/trace_result.schema.json`). Roughly 100-150 lines. CLI: `python reference/simpy/sim_core.py TRACE.json OUT.json`. No random numbers: all draws are already in the trace.
- **Semantics to reproduce exactly:** integer seconds; the five event priority levels at equal times and tie-break by `seq`; half-open windows with the whole-occupancy pre-check `[t, t + setup + service)` and no backfill; `fifo` and `edf`; sequence-dependent setup starting from each analyzer's `initial_method` in the trace; multi-visit routing with per-visit `transfer_s`; forced outcomes addressed by `(request_id, attempt, visit)`; rerun re-enqueue with `attempt + 1`; `start_s` is the run start after any setup, with `setup_s` reported; `engine_version` and `seed` copied from the trace into the result.
- **A question for you, not an answer:** SimPy orders events at the same time by a priority and an insertion counter. How will you realise five priority levels so that a run ending at `t` frees its analyzer before an arrival at `t` is enqueued and before dispatch? Record your reasoning in the header.
- **Acceptance** (`tests/user_track/test_sim_core_parity.py`): F1-F7 equal the hand expectations; the 20 engine-generated traces of `tests/golden/parity/` equal their `expected_result` exactly on integer times; output validates against the schema.
- **Learning path:** SimPy docs, "SimPy in 10 minutes", then "Topical Guides": Environments, Events, Process Interaction, Shared Resources (`Resource`, `PriorityResource`, `Store`). Run F1 by hand on paper first and keep the timeline next to your code.

Suggested order: C and A during or just after S1a; B2, B1, B3 during S2. Total about 15-20 h including learning. Do not wait for the AI path: the gates are separate.

## Reviewer instructions (any AI asked to review these files)

1. A reviewer writes the review, not the files: read-only on `reference/` (the edit guard list `.claude/user_owned.txt` is empty since ADR-0022, so this is a rule of the role). Do not run formatters or fixers on them (`ruff --fix`, `sqlfluff fix`, and similar). If the edit guard denies a write, stop; never bypass it with `bash`, `cp`, `sed` or a heredoc.
2. Run the acceptance tests and read the code against the card. Write the review to `docs/user_track/reviews/YYYY-MM-DD_<card>_<reviewer>.md` with these sections: Evidence (commands run, results), Questions, Concerns, Not reviewed.
3. A concern has a severity (blocker, major, minor), a location (`file:line`), and a **failing scenario expressed as an input** (a fixture row or a trace), not as replacement code. Quote at most three lines of the code under review per concern.
4. Questions come first and are real questions: "what happens to a result whose `available_at` equals the decision time?" Do not phrase suggestions as questions to smuggle in a rewrite.
5. If the author, writing their own version, asks for a hint, point to a documentation section or a smaller fixture; do not hand over the solution. Never edit the acceptance tests to make the code pass; if a test looks wrong, say so in the review and let the orchestrator decide.
6. Praise only what the evidence supports. Do not summarise the work as complete; the gate is the test run.
